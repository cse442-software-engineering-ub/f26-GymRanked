Contract these tests assume

Contract these tests assume

One new endpoint, api/personal_details.php, for the logged-in user only. The user always comes from the gymrank_session cookie (the same check as api/setup.php). There is no way to ask for another user's data, and any user_id sent is ignored.

GET returns 200 {"bodyweight_lb": 180.5 or null, "gender": "woman", "man", "nonbinary", "prefer_not_to_say" or null, "complete": true or false}. complete is true only when both are saved. An account that has never saved them (every account from before this feature) gets null, null, false, not an error.

POST {"bodyweight_lb": 180.5, "gender": "nonbinary"} saves both and returns the same shape as GET. Both are required: a POST that leaves one out saves nothing. Saving again replaces the old values.

bodyweight_lb is a JSON number from 50 to 700 with at most 1 decimal. gender is one of the four values above. prefer_not_to_say counts as an answer. Numbers are JSON numbers (180.5), never strings.

Errors: 401 {"error":"Please log in."}; 405 {"error":"Method not allowed."} with an Allow: GET, POST header; 400 {"error":"Invalid request.","errors":{...}} with one entry per bad field (errors.bodyweight_lb: Enter a body weight from 50 to 700 lb. errors.gender: Choose a gender.); 500 {"error":"Database error"}.


Data

New migration database/migrations/012_user_profile.sql (011 is already used on dev) creates a new table user_profile: user_id (primary key and foreign key to users, ON DELETE CASCADE), bodyweight_lb DECIMAL(4,1) NULL with a CHECK from 50 to 700, gender ENUM('woman','man','nonbinary','prefer_not_to_say') NULL, updated_at. It is a new table and not user_setup, because user_setup.experience is NOT NULL and Personal details comes before the experience step, so a new account has no user_setup row yet.

The file can be run more than once, says in its top comment how to apply it locally, on aptitude and on cattle, and changes no existing row. Existing accounts simply have no user_profile row.
